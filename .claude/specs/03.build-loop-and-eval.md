## 6. Modeling approach

### 6.1 Candidate approaches considered

| Approach | Trade-off | Verdict |
|---|---|---|
| A. One-shot generation: give the model the page and ask for a whole filler file, then test-and-fix the file | Large outputs (1–2k tokens per attempt), errors surface late and far from their cause, every fix risks regressing passing parts | rejected (intent doc v3 design) |
| B. LLM drives the browser click-by-click at run time (computer-use style) | Slow and non-deterministic per application; nothing reusable is produced | rejected (explicit non-goal) |
| C. **Step-by-step code growth**: the model writes one action, the harness runs and checks it immediately, fixes are single `edit_file` calls, passing steps are locked | Smallest possible output per round (~50–150 tokens), errors caught at the exact field, deterministic reusable code as the artifact, harness carries all verification | **chosen** (build-loop doc v1, D1, D3) |
| D. Fully deterministic heuristics (no LLM): map labels to profile keys by rules | No tokens, but brittle on custom widgets, multi-part fields and wizard navigation; still needs per-site tuning | kept as the fallback shape inside C: helpers are deterministic, the LLM only decides *which* helper call to write next |

### 6.2 Chosen model and serving

- **Model**: Qwen3-Coder-30B (local), through an OpenAI-compatible server (D5). Assumed baseline server is `llama.cpp` with a Q4_K_M GGUF; vLLM or Ollama are drop-in via `LLM_BASE_URL`. Hardware is open question Q2.
- **Sampling**: `temperature=0.1`, `top_p=0.9`, `max_tokens=400`, `seed=7` when supported. Low temperature means fewer random retries.
- **Interface**: tool calling with the schemas from `02.architecture.md` §7.3. If the server does not support `tools`, `agent/llm.py` falls back to a JSON-mode prompt (`{"tool": "...", "args": {...}}` in a single fenced block) with the same schema.
- **Server requirements**: prefix caching enabled (vLLM `--enable-prefix-caching`; llama.cpp server `--cache-prompt`; Ollama on by default). Context window ≥ 8k tokens.
- **Baselines to beat**: (1) *no-LLM heuristic* — the harness's own `suggested_next` turned directly into helper calls by rule (`fill` for text, `pick` for select with the profile value, `click` for buttons). This is implemented as `agent/heuristic.py` and run first on the fixture; the LLM must beat it on the live sites in steps completed before the first `ask_human`. (2) *one-shot generation* (approach A) is **not** implemented; the build-loop doc already rejected it.

### 6.3 Prompt design and token budget (D11, D12)

Every LLM call is assembled as a **stable prefix** + a **small task block**. The prefix is byte-identical across rounds and across companies so the server's prefix cache hits on every round after the first.

| Part | Content | Budget (tokens) | Changes |
|---|---|---|---|
| System prompt (`agent/prompts/system.md`) | role, the 8 tools in one line each, the 6 helper signatures with one-line semantics, the sandbox rules (§7.8) as 6 bullets, output rules ("one tool call; one line of why via `note` only when the choice is not obvious") | ≤ 700 | never during a build |
| Worked example | `agent/prompts/example_steps.py` (fixture-based, ~12 steps) until HCLTech is `reviewed`; then `fillers/hcltech/steps.py` when building any other SuccessFactors company (D8) | ≤ 500 | per build, not per round |
| Task block | `ObserveResult` (≤ 1,500), `done_steps: [names]` (≤ 60), `profile_keys: [...]` (≤ 80), `last_notes` (3 × ≤ 40), `last_error` (≤ 20 lines, ≤ 300), `instruction` ("Write the next step for `suggested_next` using add_step" or "Fix `step_04_phone` using edit_file: ...") | ≤ 2,300 | every round |
| **Total input** | | **≤ 2.5k typical, ≤ 3.5k p95** | |
| Output | one tool call | ≤ 300 | |

Trimming order when the cap is exceeded: drop `network`, then truncate `options` to 4, then drop `last_notes`, then drop non-required fields after the target.

**Fresh context per step**: no chat history is carried between rounds. Everything the model needs to know about the past is in `done_steps`, `last_notes`, and `last_error`.

**Few-shot for fixes**: the task block for a fix includes the failing step's current source (≤ 10 lines) and the error. The instruction says: "Replace only the wrong lines with edit_file. Do not rewrite the step."

**Approach switch** (after `SAME_ERROR_SWITCH` identical errors): the harness re-observes with `scope=<failing label>`, and swaps the worked example for the single most similar passing step (by helper + field kind) from the current or the example file. This is the only time the prefix changes mid-build; it is logged.

### 6.4 The build loop (state machine, `agent/loop.py`)

```
OPEN ──▶ OBSERVE ──▶ CLASSIFY ─┬─ login/captcha ──▶ ASK_HUMAN ──▶ OBSERVE
                               ├─ review ────────▶ FULL_TEST
                               └─ job_description | form ──▶ PROPOSE
PROPOSE  (LLM: add_step)  ──▶ RUN_STEP ─┬─ PASS ──▶ LOCK ──▶ OBSERVE
                                        └─ FAIL ──▶ FIX
FIX      (LLM: edit_file) ──▶ RUN_STEP (per D4 retry_mode) ─┬─ PASS ──▶ REGRESS
                                                            └─ FAIL ──▶ FIX | SWITCH | ASK_HUMAN | STOP
REGRESS  (replay steps 1..N-1 after any fix) ─┬─ all PASS ──▶ LOCK ──▶ OBSERVE (or FULL_TEST if it came from there)
                                              └─ any FAIL ──▶ UNDO (revert the edit, log, tell the model which step regressed) ──▶ FIX
FULL_TEST (run_checks on all samples) ─┬─ PASS ──▶ REPORT ──▶ DONE (await human review)
                                       └─ FAIL ──▶ UNLOCK(failing step) ──▶ FIX
STOP     (hard limit) ──▶ REPORT (partial) ──▶ ASK_HUMAN with log path
```

Per-build state: `rounds` (LLM calls), `tries[step]`, `same_error[step]` (count of consecutive identical normalised error strings), `locked: set[str]`, `unlocked: str | None` (at most one), `history_of_edits[step]` (for undo), `retry_mode`.

Invariants (asserted in tests):
- At most one unlocked step at any time.
- `add_step` is only accepted when `unlocked is None`.
- A locked step's source hash matches `steps.lock.json`; a mismatch aborts the build with a tamper error.
- `REGRESS` runs after **every** accepted `edit_file`, not only after full-test failures.

### 6.5 Step targets by field kind

The model writes one step per `suggested_next`; the table is what the system prompt teaches and what the fixture tests cover.

| Field kind (from observe) | Step the model should write | Check applied by the harness |
|---|---|---|
| `button` Apply | `click(page, "Apply", expect="navigation")` | URL changed or popup became current |
| `button` Next / Continue / Save and Continue | `click(page, "Next", expect="section")` | new labelled fields appeared |
| `text` / `textarea` | `fill(page, "<label>", p.<key>)` | value read back |
| `select` | `pick(page, "<label>", "<option text as shown>")` | selected text matches |
| `combobox` (SuccessFactors custom / searchable) | same `pick`; the helper opens, types, clicks the matching option | displayed value contains option |
| code + number pair (e.g. `Country Code` + `Phone Number`) | one step with `pick` then `fill` | both checks |
| `file` | `upload(page, "<label>", p.resume)` | file name visible |
| `radio` / `checkbox` | `check(page, "<label>", "Yes")` | option checked |
| `date` | `fill` in the format the field's placeholder shows | value read back |
| field not yet rendered (spinner) | `wait_for(page, "<label>")` as the first line of the step | no check of its own; the following helper's check applies |
| screening question with no profile key | step is skipped; harness adds a `report.flags` entry (D9) | — |

### 6.6 Stop conditions, retry and repair

| Condition | Counter | Action |
|---|---|---|
| Full test passes on all samples | — | Write `report.html`; log `DONE`; manifest stays `draft` until a human sets `reviewed` (D10) |
| Same step fails with the same normalised error 3× in a row | `same_error[step] == SAME_ERROR_SWITCH` | Approach switch (§6.3): scoped re-observe + similar-step example; counter continues |
| Same error 5× in a row | `same_error[step] == SAME_ERROR_ASK` | `ask_human` with the step source, the error, and the observation |
| 8 tries on one step | `tries[step] == MAX_TRIES_PER_STEP` | `STOP`: keep every locked step, write partial report, `ask_human` with log path |
| 60 rounds for the company | `rounds == MAX_ROUNDS_PER_COMPANY` | same as above |
| `page_kind` is `login` or `captcha` | — | `ask_human` immediately; never attempt to bypass; resume with the persistent browser profile |
| A fix regresses an earlier step | `REGRESS` fails | automatic `UNDO` of that edit, log row `undo`, next prompt states "your edit to step_04 made step_02 fail: <error>" |
| LLM returns no parsable tool call twice in a row | `parse_failures == 2` | re-ask once with a stricter instruction; a third failure counts as a try with error `"no tool call"` |

**Retry page state (D4)**: after a `FAIL`, compare `(url, page_kind)` with the pre-step snapshot. Equal → `retry_mode=in_place` and the fixed step re-runs on the current page. Different (the failing step navigated, or a modal is open) → `retry_mode=replay`: `goto(job_url)`, run locked steps 1..N-1, then the fixed step. Both are logged.

**Repair mode (post-v1, designed now so files stay compatible)**: `python -m agent repair <company> <failing_url>` runs locked steps until the first `FAIL`, unlocks that step only, enters `FIX`, and on success appends `failing_url` to `tests.yaml` so the fix must pass on old and new samples.

## 8. Evaluation & experimentation plan

### 8.1 Eval harness

The harness **is** the evaluation. There are three layers, cheapest first, and each layer gates the next.

| Layer | Command | Data | Gate / metric |
|---|---|---|---|
| L0 Unit + fixture (offline, no GPU, no network) | `pytest tests/ -q` | `tests/fixtures/sf_like/` (local SuccessFactors-like wizard) + `tests/fake_llm.py` | 100 % pass; runs < 2 min (N6) |
| L1 Live build | `python -m agent build <job_url>` | sample 1 of the company | reaches `review` on sample 1; metrics in `report.html` within `01.overview.md` §3 targets |
| L2 Live full test | `python -m agent test <company>` | all `tests.yaml` samples (≥ 2) | `PASS n/n`; ≤ 90 s per sample |
| L3 Benchmark rebuild | `python -m agent bench <company>` | from scratch into `runs/<company>/bench/<ts>/` (never touches `fillers/`) | rounds, tokens, first-try rate, wall-clock vs stored baseline; regression = any metric worse by > 20 % |

`run_checks` stages (used by L2 and inside the loop): (1) `ruff check` + `py_compile` on `steps.py` (< 1 s) → (2) `sandbox_check` AST (< 1 s) → (3) for each sample: `goto(url)`, run every step in order, verify its expectations, stop at `page_kind == review`, assert `expect.reaches == review` and `resume_attached` (a `FileAttached` expectation passed) and no required empty field visible. Returns only the first failure.

### 8.2 The offline fixture (L0) — what it must contain

`tests/fixtures/sf_like/` is a static multi-page form served by a `pytest` fixture on `127.0.0.1` and mimicking the SuccessFactors wizard closely enough to exercise every row of §6.5:

- `job.html`: job description; the Apply button is injected by script after 300 ms (Capgemini behaviour); a query flag `?popup=1` makes Apply open `apply_1.html` in a new tab.
- `apply_1.html`: First Name, Last Name, Email, Country Code (ARIA combobox with options like `India (+91)`), Phone Number, Resume (file input), Next.
- `apply_2.html`: Country (native select), City, Willing to relocate (radio), Work authorization (checkbox), Notice period (date-ish text), a free-text screening question with no profile key, Next.
- `review.html`: summary + a `Submit application` button (must trigger the submit guard if clicked).
- `login.html`: a password form; reachable via `?login=1` on `job.html` to test the `ask_human` path.

`tests/fake_llm.py` implements the same interface as `agent/llm.py` and replays a **script**: a list of tool calls keyed by `(state, suggested_next)`. Scripts under test:

1. **Happy path**: every step correct first time → `DONE`, `first_try_pass_rate == 1.0`, 0 fixes.
2. **Phone fix**: `step_04_phone` first uses `"+91"` → FAIL → script answers with the `edit_file` from the build-loop doc → PASS; asserts fix locality and `retry_mode == in_place`.
3. **Regression + undo**: a fix to step 5 changes a line in step 2 → `edit_file` rejected as locked; a second script variant where a legal fix makes a replay fail → `UNDO` row logged and the edit reverted.
4. **Limits**: a step that always fails → `SWITCH` at 3, `ask_human` at 5, `STOP` at 8; partial report written; locked steps intact.
5. **Submit guard**: a script that tries `click(page, "Submit application")` → `ForbiddenAction`, step rejected, log row present.
6. **Login**: `?login=1` → `page_kind == login` → `ask_human` called; fake human "logs in" (fixture sets a cookie) → loop resumes.
7. **Popup Apply**: `?popup=1` → `click(..., expect="navigation")` switches current page; next observe sees `apply_1` fields.
8. **Token caps**: an `apply_1` variant with 120 fields → observe truncates to ≤ 1,500 tokens and sets `truncated: true`.
9. **Masking**: after any run, no profile value, `password`, or `cookie` string appears in `actions.jsonl`, `actions.md`, or `report.html`.

### 8.3 Offline → live gating

1. L0 green on the branch.
2. `python -m agent build` on the fixture with the **real** Qwen server (`tests/live_fixture_smoke.py`, manual): the model, not the script, must reach `review` on the fixture within 25 rounds. This is the first real check of prompt quality and server latency, and sets the latency baseline.
3. HCLTech live build (T19), then full test with ≥ 2 samples.
4. Capgemini live build with HCLTech as the example (T20); first-try rate must be ≥ 80 %.
5. Benchmark rebuild of both (T21) and record baselines in `runs/<company>/bench/baseline.json`.

### 8.4 Experiments / ablations (run with `bench`, logged by run id)

| Experiment | Question | Measure |
|---|---|---|
| E1 example on/off | Does the worked example lift first-try rate? | first-try rate, rounds |
| E2 `suggested_next` on/off | How much does the harness hint save? | rounds, output tokens |
| E3 options preview 8 vs 4 vs 0 | Trade input tokens for `pick` accuracy | `pick` first-try rate, tok_in |
| E4 temperature 0.1 vs 0.3 | Does more randomness help escape identical-error loops? | `same_error` switches, rounds |
| E5 fresh context vs last-3-rounds history | Is D12 costing accuracy? | first-try rate, tok_in |
| E6 HCLTech example vs fixture example for Capgemini | Validates D8 | Capgemini first-try rate |

"Good enough to ship v1" = L2 `PASS n/n` on both companies with all `01.overview.md` §3 guardrails met; experiments E1–E6 are for tuning, not gating.

### 8.5 Regression & guardrail checks (must never regress)

- `pytest tests/` stays green on every change to `core/` or `agent/`.
- Submit guard test, masking test, sandbox test, and host-allowlist test are tagged `@pytest.mark.safety` and run first.
- `python -m agent test <company>` for every `reviewed` filler before any prompt or helper change is merged (manual in v1, since it needs the live sites and a login).

## 11. Rollout, monitoring & lifecycle

- **Rollout**: v1 is a local tool with no users besides the owner. "Rollout" means: filler `draft` → human review of `report.html` (diff, per-sample results, flags) → `status: reviewed` → the filler may be run with the real profile in a later live-mode spec. Rollback is `git revert` of the filler directory or deleting it; nothing else depends on it.
- **Monitoring**: every run produces `report.html` with the §3 metrics; `bench` results accumulate under `runs/<company>/bench/`. A weekly manual `python -m agent test <company>` is the drift smoke test (§5.4). Alert thresholds: any `PASS < n/n`, any `tok_in > 3.5k` row, any safety row (`ForbiddenAction`, blocked host, `[redacted line]`) in a log.
- **Lifecycle**: a filler is "retrained" only through repair mode (one step at a time) or a full `bench` rebuild when the form changes drastically. Ownership is the project owner. The harness version in `manifest.built_with` tells which helpers a filler was built against; a helper signature change bumps the harness minor version and requires re-running `test` on all fillers.
