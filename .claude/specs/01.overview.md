## 1. Context & problem statement

Applying to jobs on large company career sites means filling the same SAP SuccessFactors apply wizard again and again. Each company's form differs only in small ways (labels, locale, extra questions), and the same company's form is identical across job IDs.

The project is a **builder agent** that, given one job-posting URL, uses a local LLM (Qwen3-Coder-30B) to write a **form filler** for that company, tests the filler on 2–3 sample postings from the same company, and saves it in a fixed, reusable package. Later job posts from that company reuse the saved filler instead of triggering a rebuild.

The two source documents disagree on *how* the filler is shaped:

- The intent doc (13 Oct) describes a per-company `resolver.py` + `fields.yaml` and a per-application-system `driver.py` written by the LLM against a fixed interface.
- The build-loop doc (14 Oct) replaces that with a per-company `steps.py` that grows **one browser action at a time**, each action tested in the live browser the moment it is written, and fixed by replacing only the broken lines. It explicitly notes the intent doc must be brought in line.

This suite adopts the **step-by-step `steps.py` model as canonical** (decision D1, §13) and keeps the intent doc's durable goals: build once per company, reuse across job IDs, never submit without human review, never put personal data in generated code or logs.

Today nothing exists in the repo except the two HTML docs. Everything in this suite is new work.

**One-paragraph summary.** Paste a job URL. The harness opens it in Playwright, trims the page to an accessibility-tree summary, and asks Qwen to write the code for exactly one action (click Apply, fill name, pick country code + fill phone, upload resume, click Next…). The harness runs that one step in the live browser, checks it (value read back, or the next page appeared), and either locks it or hands the first error back to Qwen for a minimal `edit_file` fix. This repeats to the final review page, never pressing Submit. A full test then replays all steps from the job link on every sample posting. When all pass, a review report is produced and, after human approval, the filler is saved under `fillers/<company>/`. The first two targets are HCLTech and Capgemini, both on SuccessFactors.

## 2. Goals & non-goals

**Goals (v1 commits to these)**

- G1. A hand-written **harness** (`core/` + `agent/`) exposing eight tools to the LLM: `observe`, `read_file`, `add_step`, `edit_file`, `run_step`, `run_checks`, `note`, `ask_human`. The LLM reaches the world only through these.
- G2. A **build loop** that produces `fillers/hcltech/steps.py` and `fillers/capgemini/steps.py`, each passing `run_checks` on all of that company's sample URLs in `tests.yaml`, reaching the final review page with every required field filled and the resume attached, without pressing Submit.
- G3. **Minimal-edit repair**: once a step passes it is locked; a fix is one `edit_file` inside the one failing step; a fix that breaks an earlier step is auto-undone.
- G4. A complete **action log** (`actions.jsonl` + `actions.md`) per run with per-round token and time accounting, masked of all profile values and credentials.
- G5. **Token discipline** so each round stays fast on a local 30B model: ≤ 2.5k input / ≤ 0.3k output tokens per round (targets in §3), stable prompt prefix for server-side prefix caching, fresh context per step.
- G6. A **dummy candidate profile** used for every test fill; switching to the real profile later is a file path change only.
- G7. An **offline fixture** (local SuccessFactors-like form + scripted fake LLM) so the whole loop is testable with `pytest` before any live site or GPU is involved.

**Non-goals (explicitly out of v1)**

- Searching for jobs or deciding where to apply.
- The **reuse lookup** (matching a new URL against saved fillers before building). Every URL triggers a build in v1. Files are saved in the reusable format so the lookup can be added without changing them.
- Bypassing CAPTCHAs, bot protection, or login walls. The agent stops and asks the human.
- Submitting any application. `core/submit.py` exists only as a guarded stub; the live-submit path is a later spec.
- Letting the LLM drive the browser click-by-click at run time. The LLM writes code inside the framework; deterministic code fills forms.
- The job-API shortcut for Capgemini (going straight to the apply URL from `cg-jobstream-api`). Kept as a noted speed-up; step 1 is "click Apply".
- A shared SuccessFactors step library. Deferred until both companies pass (decision D8).
- LLM-drafted answers to free-text screening questions. v1 leaves them blank and flags them in the report (decision D9).

## 3. Success metrics

All offline metrics are computed by `agent/report.py` from `actions.jsonl` (schema in `02.architecture.md` §7.6). "Round" = one LLM call plus the harness work it triggers.

| Type | Metric | Target / threshold | How measured |
|---|---|---|---|
| Offline | Companies whose `steps.py` passes `run_checks` on all samples | 2 / 2 (HCLTech, Capgemini) | `python -m agent test <company>` → `PASS n/n` |
| Offline | Fixture end-to-end loop passes with fake LLM | 100 % of `tests/test_loop_fixture.py` | `pytest tests/` |
| Offline | Step first-try pass rate (`run_step` PASS on the first `add_step`) | HCLTech ≥ 60 %; Capgemini ≥ 80 % (built with HCLTech as example) | report: `first_try_pass_rate` |
| Offline | Rounds per company build | ≤ 40 (hard stop 60) | report: `rounds_total` |
| Offline | Tries per step | median ≤ 2 (hard stop 8) | report: `tries_per_step` |
| Offline | Fix locality | 100 % of fixes are `edit_file` calls touching one unlocked step | enforced by `agent/steps_file.py`; report counts violations = 0 |
| Offline | Regressions surviving a fix | 0 (any regression is auto-undone and logged) | report: `regressions_undone`, `regressions_open = 0` |
| Online (later, real runs) | Real job posts reaching review page on a saved filler | ≥ 95 % | fill report per run |
| Online (later) | Human time per application review | ≤ 2 min | manual timing |
| Guardrail | Input tokens per round | ≤ 2.5k (p95 ≤ 3.5k) | log `tok_in` |
| Guardrail | Output tokens per round | ≤ 0.3k | log `tok_out` |
| Guardrail | Tokens per company build (sum in+out) | ≤ 150k | report |
| Guardrail | Wall-clock per company build (excluding `ask_human` waits) | ≤ 20 min | report |
| Guardrail | `run_checks` time per sample | ≤ 90 s | log `s` on `run_checks` |
| Guardrail | `observe` payload | ≤ 1,500 tokens (chars/4) | assertion in `core/observe.py` + test |
| Guardrail | Round latency on the chosen local server (≤ 2.5k in) | ≤ 8 s p50 (set after T21 benchmark; record baseline) | log `s` on qwen rounds |
| Safety | Submit presses during build/test | 0 | submit guard raises `ForbiddenAction`; test asserts |
| Safety | Profile values, passwords, cookies in any log/report/prompt | 0 occurrences | `tests/test_log.py` scanner + `agent/report.py` scan |
| Safety | Requests to hosts outside the company allowlist from generated steps | 0 | Playwright route block + log count |
| Safety | CAPTCHA / login bypass attempts | 0 | loop stops with `ask_human`; test on fixture login page |

Unknown baselines: round latency and first-try pass rate have no baseline yet. The first HCLTech build (T19) and the benchmark (T21) establish them; targets above are the commitment, adjusted only with a logged decision.

## 4. Requirements

### 4.1 Functional

- F1. `python -m agent build <job_url>` opens the URL, derives the company from the host, creates `fillers/<company>/` if missing, and runs the build loop to the review page or a stop condition.
- F2. `python -m agent test <company>` runs the full check (lint → sandbox → fill on every `tests.yaml` sample) and prints only the first failure, or `PASS n/n`.
- F3. The LLM can only call the eight tools in `02.architecture.md` §7.3; it cannot run shell, read credentials, or submit.
- F4. Steps call only the helpers `click`, `fill`, `pick`, `upload`, `check`, `wait_for` from `core.helpers`. Raw Playwright calls in generated code are rejected by the sandbox check.
- F5. Each helper registers the check that proves it worked (value read back, option selected, file name shown, page changed). The harness verifies after the step runs. The LLM writes no asserts.
- F6. Field types supported in v1: button, text box, native dropdown, custom/searchable dropdown (SuccessFactors combobox), phone (code + number), file upload, radio/checkbox, date, multi-page Next/Continue, new-tab navigation on Apply (Capgemini).
- F7. Stop conditions (`03.build-loop-and-eval.md` §6.4): same-error ×3 → change approach; ×5 → ask; 8 tries/step; 60 rounds/company; login or CAPTCHA → ask immediately; fix regresses an earlier step → auto-undo.
- F8. Every run writes `runs/<company>/<timestamp>/{probe/, actions.jsonl, actions.md, report.html, screenshots/}`.
- F9. The dummy profile `profiles/dummy.yaml` and a generated one-page `profiles/dummy_resume.pdf` are the only candidate data used until a filler's manifest `status` is `reviewed`.
- F10. Persistent browser profile per site under `browser_profiles/<site>/` so a human logs in once; the loop resumes after `ask_human` returns.

### 4.2 Non-functional

- N1. Runs on the owner's local machine (Windows 11), Python ≥ 3.11, Playwright Chromium. The LLM is served by an OpenAI-compatible local server (vLLM, llama.cpp server, or Ollama); the client is configured by `LLM_BASE_URL` and `LLM_MODEL` only.
- N2. No personal data, credentials, cookies, or real resume leaves the machine, enters generated code, prompts, logs, or reports. Credentials come from `.env` or the OS keychain at run time only.
- N3. Generated code is sandboxed: allowlisted imports, no `page.*` access, no network outside the manifest's `allowed_hosts`, no submit.
- N4. Deterministic where possible: temperature ≤ 0.2, fixed seed when the server supports it, snapshots cached per URL and reused across tries.
- N5. Everything under `runs/`, `browser_profiles/`, `.env`, and `profiles/real*` is git-ignored.
- N6. The offline fixture test suite runs in under 2 minutes without a GPU or network.

## 10. Risks & mitigations

| Risk | Likelihood | Impact | Mitigation / fallback |
|---|---|---|---|
| Both sites require a candidate account and allow one real account per person, so test fills would use the real account | Med | High | `ask_human` on login; dummy data only; never submit; open question Q1. If no test account is possible, test fills run on the real account but with dummy field values and stop at review. |
| Login requirement unconfirmed (apply page redirected to homepage without a session) | High | Med | `page_kind == login` classifier + `ask_human`; persistent browser profile so it happens once per site. |
| SuccessFactors custom comboboxes (country code, country) do not accept `select_option`; option text differs from what the LLM guesses (`+91` vs `India (+91)`) | High | Med | `pick` handles both native and ARIA combobox; `observe` includes an `options_preview` (first 8 options) so the LLM copies exact text; error message lists matching options. |
| Capgemini "Apply" opens `careers.capgemini.com` in a new tab | High | Med | `click(expect="navigation")` waits for popup or same-tab navigation and switches the harness's current page. Covered by fixture test. |
| Capgemini job page is filled by script from `cg-jobstream-api`; Apply button not present on first paint | High | Low | `observe` waits for network idle + the Apply button; `wait_for` helper available to steps. |
| Local 30B model is too slow on the owner's hardware (unknown GPU / quantization) | Med | High | Token budget (§3), prefix caching, structured output; benchmark in T21; model and server swappable via env vars. |
| Qwen tool-calling is unreliable through some servers (malformed JSON, prose instead of a call) | Med | Med | `agent/llm.py` parses tool calls, falls back to a fenced-JSON parse, and on 2 consecutive parse failures re-asks with a stricter reminder; counts as a try. |
| Accessibility tree on SuccessFactors pages is large (hidden wizard pages, duplicate nodes) | High | Med | Trim rules in `02.architecture.md` §7.4; hard cap 40 fields and 1,500 tokens with `+N more`; section-scoped observe on retry. |
| Flaky timing (field not ready, spinner) causes false FAILs and wasted rounds | High | Med | Helpers auto-wait for visibility/enabled; `wait_for` helper; retry-in-place policy; `run_step` FAIL message says whether the element was found. |
| A generated step accidentally submits | Low | High | `click` refuses text matching the submit regex in build/test mode; `core/submit.py` never imported by the build path; test asserts both. |
| Profile values or secrets leak into logs or prompts | Med | High | `core/log.py` masks all profile values; secrets never loaded in build mode; scanner test over every log and report. |
| Site DOM changes break a saved filler weeks later | High (over time) | Med | `tests.yaml` smoke run; repair mode (post-v1) fixes only the failing step; failing URL added to samples. |
| Locale and label differences between `en_GB` (Capgemini) and `en_US` (HCLTech) forms | Med | Low | Label matching is case-insensitive and strips `*` and `:`; each company has its own `steps.py` anyway. |
| Bot protection on the Capgemini job page or API (Cloudflare challenge) | Low | High | `page_kind == captcha` → stop and ask; never attempt bypass. |
| The real resume PDF stored under `my-docs/` gets used by mistake | Low | High | Profile loader refuses any `resume` path outside `profiles/`; dummy profile points at `profiles/dummy_resume.pdf`; real profile is a separate git-ignored file. |

### Decisions (ADR-style)

- **D1 — `steps.py` per company is the canonical filler format; resolver/driver/fields.yaml are dropped.** Context: the 14 Oct build-loop doc supersedes the 13 Oct intent doc and asks for the reconciliation. Consequences: filler package = `manifest.yaml` + `steps.py` + `tests.yaml` (+ `steps.lock.json`); "same code for the same company" is proven by one `steps.py` passing on all samples; the SuccessFactors commonality is captured later by promoting duplicated steps into a shared library (D8), not by a driver written up front.
- **D2 — No reuse lookup in v1, but `manifest.yaml` must carry `url_patterns` and `application_system`.** Context: both docs defer the lookup. Consequences: every URL builds; the later lookup needs only a matcher over manifests, no format change.
- **D3 — Helpers carry their own checks; the LLM writes no assertions.** Context: a 30B model writing both action and verification doubles output and error surface. Consequences: `core/helpers.py` records expectations in a step context; `run_step` verifies them; a step's "check" is fully determined by the helpers it called.
- **D4 — Retry in place when the page is unchanged; replay from the job link when it is not.** Context: Q6. Consequences: after a `run_step` FAIL the harness compares URL and `page_kind` to the pre-step snapshot; if equal, the fixed step re-runs on the current page; otherwise steps 1..N-1 replay (login persisted) and then the fixed step runs. Logged as `retry_mode`.
- **D5 — OpenAI-compatible local server; model and server are config, not code.** Consequences: `agent/llm.py` uses the `openai` SDK with `base_url`; swapping Qwen for another coder model changes `LLM_MODEL` only.
- **D6 — Dummy profile only until a filler is `reviewed`.** Consequences: `profiles/dummy.yaml` + generated `dummy_resume.pdf`; the loader refuses resume paths outside `profiles/`.
- **D7 — Step 1 is "click Apply", not a job-API resolver.** Context: build-loop doc. Consequences: Capgemini's new-tab navigation must be handled by `click`; the API shortcut stays a noted optimization.
- **D8 — Shared SuccessFactors step library is deferred.** Context: avoid designing an abstraction before two concrete instances exist. Consequences: Capgemini is built with HCLTech's `steps.py` as the worked example; after both pass, identical steps may be promoted to `core/successfactors.py` in a later spec.
- **D9 — Free-text screening questions are left blank and flagged in the report in v1.**
- **D10 — Human review is required before `status: reviewed`;** the harness never writes `reviewed` itself.
- **D11 — Observation is trimmed accessibility tree + network summary, never raw HTML;** hard cap 1,500 tokens.
- **D12 — Fresh context per step.** Each LLM call gets the stable system prefix plus only: current observation, names of passed steps, profile keys, last 3 notes, last error (≤ 20 lines). No conversation history is carried.
