Job Form Agent

An agent that creates form fillers. Given a job posting URL, it builds an automated filler for that company's application form, tests it, and saves it in a fixed, reusable format. The next job post from the same company or application system reuses the saved filler instead of building a new one. The building is done by a local LLM, Qwen3-Coder-30B.

Main rule: build once, reuse for every job post. A filler is made for a company or application system, never for one job ID. For now, when a new URL comes in, the agent opens it in the browser and starts building the filler straight away. Checking whether a saved filler already covers the URL is a later step (see section 9).

1. What I want

There are two parts:

PART A: BUILDER AGENT

Creates the fillers

  • Takes a job URL.
  • Opens the job link in the browser and starts building right away. It doesn't check for existing code yet.
  • Looks at the site (links, application system, form fields, network calls) and has Qwen write a filler in the standard format.
  • Tests the new filler on 2–3 job posts from the same company and fixes it until it passes.
  • Saves it to the registry, so the later reuse step has something to find.
PART B: FORM FILLER (generated)

Fills the forms, reused across job posts

  • A saved package in the standard format (see section 2).
  • Works for any job post that matches its URL patterns. Only the job ID changes.
  • Fills fields from my profile, uploads my resume, and handles multi-step forms.
  • Pauses before the final submit for my review.

Example: the builder creates a filler from capgemini.com/…/jobs/196626-en_GB+sap_btp. Then 355474 and 220549 run on that same filler with no new code. careers.hcltech.com/…/180703-en_US gets its own filler, but because HCLTech also runs on SuccessFactors, that filler reuses the same SuccessFactors steps and only needs its own settings.

2. The reusable filler format

Every filler the builder creates has the same layout, so any filler can be loaded, run, tested and reused the same way:

fillers/
  successfactors/            ← shared steps for this application system (driver)
    driver.py                   login, apply wizard, page navigation, upload
  capgemini/                 ← one folder per company
    manifest.yaml               name, URL patterns, application system, version, status
    resolver.py                 job URL → real apply URL (capgemini: via job API)
    fields.yaml                 form label → profile field, plus saved answers to known questions
    tests.yaml                  2–3 sample job URLs the filler must pass
  hcltech/
    manifest.yaml
    resolver.py
    fields.yaml
    tests.yaml

4. How it's built

job URL
   │
   ▼
Open in browser (no existing-code check for now)
   │
   ▼
Code-gen loop (Qwen) ── writes ──▶ Resolver (one per company)  ──▶ real apply URL
   │                                    │
   │                                    ▼
   │                         System check (SuccessFactors? Workday? …)
   │                                    │   detected from fixed markers, not by the LLM
   │                                    ▼
   └── writes ──────────────▶ Driver (one per system) + settings (one per company)
                                        │
                                        ▼
                        Shared core: browser · profile · label matching ·
                        resume upload · screening answers · review report · SUBMIT
  • Shared core (written by hand, not by the LLM): browser control, the candidate profile, matching fields by their label text, file upload, the review report, and the only code that can press submit.
  • Driver per system: SuccessFactors first. It handles login, the steps of the apply form, and moving between pages.
  • Resolver and settings per company: small, and the easiest part for Qwen to write correctly.
  • System check: plain rules that look for known markers (rmkcdn.successfactors.com, /talentcommunity/apply/, myworkdayjobs.com, …). A known system never triggers a new driver.

5. The LLM: Qwen3-Coder-30B (local)

What it does

  • When setting up a new site: writes the missing resolver, settings file or driver, and fixes them until their tests pass.
  • When filling a form: only drafts answers to screening questions the profile can't answer, as structured output that is marked for my review. Deterministic code does the actual filling, not the LLM.

Making a 30B local model reliable

  • Small, fixed targets. Qwen writes code against a fixed interface (resolve(url) → apply_url, Driver.fill(page, profile)), not a whole scraper. Settings use a JSON/YAML schema it has to follow.
  • Settings before code. If a company is on a known system, Qwen only writes a settings file. It writes a resolver only if one is missing, and a driver only for a system nobody has covered yet.
  • Worked example in every prompt. Include an existing working resolver or driver (the Capgemini one once it's done) as the pattern to copy.
  • Trimmed page content. Give it the form's fields, labels and buttons (the accessibility tree) and the network calls the page made, not the full raw HTML. That keeps the prompt within what the local machine can handle.
  • Test-and-fix loop. Generate → run a test fill (fills fields, never submits) on 2–3 sample URLs → send errors and a screenshot description back to Qwen → repeat up to N times. Passing on all samples is the proof of "same code for the same company".
  • Low temperature for code. Use an OpenAI-compatible local server (vLLM, llama.cpp or Ollama) so the model can be swapped later without changing the agent.
  • Guardrails on generated code. It runs in a sandbox with a list of allowed imports. It can't submit forms, read credentials directly, or make network calls outside the target site. I review it before it goes into the registry.

6. How a run goes

  1. Decode the URL, open it in the browser, and start the code-gen loop straight away to build the filler. (No check for existing code for now.)
  2. The resolver produces the real apply URL (Capgemini: through the job API).
  3. Detect the application system and load its driver plus the company's settings.
  4. Open the browser with the saved login for that site and go to the apply form.
  5. Fill fields from the profile. Use saved answers from earlier runs on that site, and ask Qwen only about questions it can't answer.
  6. Pause before the final submit and show the report: filled fields, empty fields, and AI-drafted answers.
  7. Submit only after I confirm.

7. Candidate profile and logins

My details live in one local profile file plus my resume. Logins for each site are stored in .env or the OS keychain, and each site keeps its own saved browser profile so I only log in by hand once. None of this goes into generated code, prompts sent outside the machine, logs or reports.

8. Adding a new company later

  1. Paste a URL. The agent opens it and starts building. (Later, the reuse lookup will skip this when a saved filler already matches.)
  2. If it's a new company on a known system, Qwen writes a resolver and a settings file.
  3. If it's a new system, Qwen writes a driver as well, starting from the SuccessFactors driver as the example.
  4. Every new piece has to pass a test fill on 2–3 postings, and I review it before it's saved.

9. Out of scope (for now)

  • Searching for jobs or deciding which jobs to apply to.
  • Checking whether code for a site already exists before building. This reuse lookup will be designed later.
  • Getting around CAPTCHAs or bot protection. The agent stops and hands control to me.
  • Submitting without my review.
  • Letting the LLM drive the browser freely, click by click. It writes code inside the framework and doesn't operate the browser itself.

10. Still to decide

  • Confirm that both sites need a candidate account, and create one for each.
  • What hardware and which quantization will serve Qwen3-Coder-30B, and which local server (vLLM, llama.cpp or Ollama)?
  • Free-text screening questions: leave them blank, or let Qwen draft answers for my review?
  • Does every generated piece need my manual review, or is passing the tests enough for settings-only changes?

5. LLM: Qwen3-Coder-30B (local)

Ye kya karta hai

  • Nayi site setup karte waqt: missing resolver, settings file ya driver likhta hai, aur tests pass hone tak unhe fix karta hai.
  • Form bharte waqt: sirf un screening questions ke answers draft karta hai jo profile se nahi bhar sakte, structured output mein, aur wo mere review ke liye mark hote hain. Asli filling deterministic code karta hai, LLM nahi.

30B local model ko reliable kaise banayein

  • Chhote, fixed targets. Qwen ek fixed interface (resolve(url) → apply_url, Driver.fill(page, profile)) ke against code likhta hai, poora scraper nahi. Settings ek JSON/YAML schema follow karti hain jo use maanna padta hai.
  • Code se pehle settings. Agar company kisi known system par hai, toh Qwen sirf settings file likhta hai. Resolver tabhi likhta hai jab wo missing ho, aur driver sirf us system ke liye jo abhi tak kisi ne cover nahi kiya.
  • Har prompt mein ek worked example. Ek existing, chalta hua resolver ya driver (Capgemini wala, ban jaane ke baad) copy karne ke pattern ki tarah do.
  • Trimmed page content. Use form ke fields, labels aur buttons (accessibility tree) aur page ke network calls do, poora raw HTML nahi. Isse prompt utna hi rehta hai jitna local machine handle kar sake.
  • Test-and-fix loop. Generate → 2–3 sample URLs par test fill chalao (fields bharta hai, kabhi submit nahi karta) → errors aur screenshot ka description Qwen ko wapas bhejo → N baar tak repeat karo. Saare samples par pass hona hi "same company ke liye same code" ka proof hai.
  • Code ke liye low temperature. OpenAI-compatible local server (vLLM, llama.cpp ya Ollama) use karo, taaki baad mein agent badle bina model swap ho sake.
  • Generated code par guardrails. Ye sandbox mein allowed imports ki list ke saath chalta hai. Ye forms submit nahi kar sakta, credentials seedha nahi padh sakta, aur target site ke bahar network calls nahi kar sakta. Registry mein jaane se pehle main ise review karta hoon.

6. Ek run kaise chalta hai

  1. URL decode karo, browser mein kholo, aur filler banane ke liye seedha code-gen loop shuru karo. (Abhi existing code ka check nahi.)
  2. Resolver asli apply URL deta hai (Capgemini: job API ke through).
  3. Application system detect karo aur uska driver plus company ki settings load karo.
  4. Us site ke saved login ke saath browser kholo aur apply form par jao.
  5. Profile se fields bharo. Us site ke pichhle runs ke saved answers use karo, aur Qwen se sirf wahi questions poocho jo wo khud answer nahi kar sakta.
  6. Final submit se pehle ruko aur report dikhao: bhare hue fields, khaali fields, aur AI-drafted answers.
  7. Mere confirm karne ke baad hi submit karo.

7. Candidate profile aur logins

Meri details ek local profile file aur mere resume mein rehti hain. Har site ke logins .env ya OS keychain mein store hote hain, aur har site ka apna saved browser profile hota hai, taaki mujhe sirf ek baar haath se login karna pade. Inme se kuch bhi generated code, machine ke bahar jaane wale prompts, logs ya reports mein nahi jaata.

8. Baad mein nayi company add karna

  1. URL paste karo. Agent use kholta hai aur banana shuru karta hai. (Baad mein, saved filler match hone par reuse lookup yeh step skip karega.)
  2. Agar ye known system par nayi company hai, toh Qwen ek resolver aur settings file likhta hai.
  3. Agar ye naya system hai, toh Qwen ek driver bhi likhta hai, SuccessFactors driver ko example maan kar.
  4. Har naye piece ko 2–3 postings par test fill pass karna padta hai, aur save hone se pehle main use review karta hoon.

9. Abhi scope ke bahar

  • Jobs dhoondhna ya decide karna ki kahan apply karna hai.
  • Banane se pehle check karna ki site ka code pehle se hai ya nahi. Yeh reuse lookup baad mein design hoga.
  • CAPTCHAs ya bot protection ko bypass karna. Agent ruk jaata hai aur control mujhe de deta hai.
  • Mere review ke bina submit karna.
  • LLM ko browser freely, click-by-click chalane dena. Ye framework ke andar code likhta hai, browser khud nahi chalata.

  • Kya har generated piece ko mera manual review chahiye, ya settings-only changes ke liye tests pass hona kaafi hai?
