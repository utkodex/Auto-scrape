Code Build Loop

How the builder agent writes the form-filler code for HCLTech and Capgemini, one step at a time, and keeps fixing it until it works. As soon as the browser opens the job link, building starts right away: there is no "do we already have code for this?" check for now. Then it looks at the page, writes the code for one action, runs it in the browser, and fixes only the broken lines if it fails, step after step. It records every action in a log and uses dummy candidate data. It also uses as few tokens as it can so each round stays fast on a local Qwen3-Coder-30B.

Main rule: the loop only stops when every check passes on every sample URL, or when it hits a hard limit and hands over to me with the log. "It looks right" doesn't count as done. Done means the tests passed.
For now: link in → browser opens the job post → the agent starts building the filler straight away. It does not look for existing code first. The system that checks for and reuses saved fillers comes later (see section 8).

1. What this doc covers

  • The build loop: how the code is built one step at a time (click Apply, then name, email, phone…), each step tested as soon as it's written, with only the broken part replaced when something fails.
  • The first two targets: HCLTech careers.hcltech.com/job/…/180703-en_US and Capgemini capgemini.com/in-en/jobs/196626-en_GB+sap_btp.
  • The action log: a note of every step the agent takes while building.
  • Dummy data: a fake candidate profile used for all test fills.
  • The harness: the agent works with the same observe → edit → run → read-result tool loop that a coding agent like Claude Code uses.
  • Token saving: the methods that keep prompts small so code is created quickly.

This is a plan only. No code has been written or changed yet.

2. The harness: same pattern as a coding agent

The builder agent doesn't get one giant prompt and return a finished file. It works the way a coding agent does: a short loop of small tool calls, where each result decides the next step. Qwen is the model inside the loop. The harness around it is plain code.

ToolWhat it doesLike Claude Code's
observe(url)Opens the page in Playwright and returns a trimmed view: form fields, labels, buttons (accessibility tree) and the network calls made. Cached per URL.Read / WebFetch
read_file(path, lines?)Reads part of an existing file, such as the worked example, the interface, or the current draft.Read
add_step(name, code)Adds one new step to the end of steps.py. It can't overwrite a step that already passed.Write
edit_file(path, old, new)Replaces one exact piece of text inside the failing step. Used for every fix.Edit
run_step(name)Runs only the newest step in the live browser, from where the page is now, then runs that step's check (value read back, or the next page appears).Bash (one quick run)
run_checks(target)The full test. Runs, in order: syntax/lint → sandbox rules → all steps from the job link on every sample job (never submits). Returns only the first failure.Bash (tests)

  • Qwen can only reach the outside world through these tools. It can't run arbitrary shell commands, submit forms, or read credentials.
  • Paths are limited to the one filler folder being built (for example fillers/hcltech/), plus read-only access to the shared core and the worked example.
  • Tool results are short by design (see section 6). Each one carries just enough for the next decision.

3. The build loop: one step at a time

The agent builds the filler the way a person learns a new form: look at the page, do one thing, check that it worked, then move on to the next thing. The code grows one small step at a time, and each step is run in the live browser the moment it's written.

Walkthrough (HCLTech as the example)

  1. Open. The browser opens the job link. If a login page shows up, ask_human runs and I log in once.
  2. Look. observe reads the page. It's a job description with an "Apply" button, not a form.
  3. Step 1: click Apply. Qwen writes step_01_click_apply. run_step runs it. The form page appears, so the step passes and is saved.
  4. Look again. Now it's a form. Fields found: first name, last name, email, phone (a country code dropdown plus a number box), resume upload, and so on.
  5. Step 2: name. Qwen writes step_02_name. It runs, then the harness reads the boxes back to confirm the values went in.
  6. Step 3: email. Same as name.
  7. Step 4: phone. The agent sees two parts: a dropdown for the country code and a box for the number. It writes one step that fills both, runs it, and checks that the dropdown shows India (+91) and the box shows the number. If the first try picks the dropdown option the wrong way, Qwen gets the error and changes only those lines.
  8. Keep going. One field at a time. At a Next button it clicks, looks at the new page, and carries on. It stops at the final review page and never presses submit.
  9. Full test. Run every step from the job link on 2–3 sample jobs. If something breaks on one of them, for example the resume upload isn't ready yet on the second job, it finds the failing step and replaces only that part.
  10. Review and save. I see the report, then steps.py is saved in fillers/<company>/.

Fixing: replace only the wrong part, never the whole code

  • The code is never regenerated from scratch. Once a step passes, it's locked. Qwen can only change it if a later test shows that exact step is the one failing.
  • A fix is one edit_file call: the exact wrong lines → the right lines, inside the one failing step.
  • After every fix, the earlier steps run again. If any of them now fails, the fix is undone automatically.
# step_04_phone, first try. Failed: "no option '+91'. Options look like 'India (+91)'"
pick(page, "Country Code", "+91")

# the only line Qwen replaced
pick(page, "Country Code", "India (+91)")

How each field type is handled

Qwen doesn't write raw browser code for each field. It calls small hand-written helpers (click, fill, pick, upload, check), usually one line per field.

When the loop stops

ConditionWhat happens
Full test passes on all 2–3 sample jobsWrite a review report (diff, test results, log summary). I review it, and only then is it saved in fillers/<company>/.
Same step fails the same way 3 times in a rowChange approach: observe that part of the page again, and show Qwen a similar working step as the example. If it still fails 2 more times, ask me.
Hard limit: 8 tries per step, or 60 per companyStop, keep every step that passed, and ask me, with the log attached.
Login wall or CAPTCHAStop at once and ask me. Don't try to get around it. Resume after I've logged in with the saved browser profile.
A fix breaks an earlier stepUndo that edit automatically, log it, and tell Qwen which step went backwards.

What "right" means (the checks)

  1. Each step runs on the live page and its own check passes (value read back, or the next page appears).
  2. The file is valid Python and passes lint.
  3. Sandbox rules: only the helpers and allowed imports, no submit call, no reading of credentials, no network calls outside the target site.
  4. The full test, starting from the job link, reaches the final review page on every sample job, with every required field filled and the resume attached.
  5. The same steps.py passes on every sample job for that company. This proves "same code for the same company".

Improving later (after it works)

  • Every real run also writes a fill report. If a run fails because the site changed, the loop starts in repair mode: it runs the saved steps until the one that fails, and fixes only that step.
  • The failing job link gets added to tests.yaml, so the fix has to pass on the old samples and the new one.
  • Fixes are small edits, so the diff I review stays short.

5. Action log: notes of everything the agent does

Every tool call and every decision is written down as it happens, so I can follow the build afterwards and see why it failed or passed.

  • actions.jsonl: one line per action, machine-readable.
  • actions.md: the same steps in plain sentences, readable at a glance.
  • Fields: time, round, actor (qwen / harness / human), tool, short input, result (pass/fail plus a one-line reason), tokens in/out, seconds taken.
  • The log never contains passwords, cookies, or real personal data. Field values from the profile are masked (first_name=***).

6. Using fewer tokens so the code is created faster

On a local 30B model, fewer tokens means faster rounds. Each method below cuts what goes into or comes out of the model.

MethodSaves
Edits, not rewrites. Qwen never resends the whole file. A fix is an edit_file call (old text → new text) inside one step.Output: a fix is around 100 tokens instead of a 1,500-token file.
One step at a time. Each prompt is about one action on one page: the trimmed view of that page, the names of the steps done so far, and the profile keys.Input: small prompts, and mistakes are caught at the field where they happen.
Helpers, not raw browser code. Qwen calls click / fill / pick / upload / check, usually one line per field.Output, and fewer browser-timing bugs.
Trimmed page view. Accessibility tree plus network calls, never raw HTML. Drop hidden, decorative and duplicate nodes.Input: often 50–100× smaller than the HTML.
Probe once, reuse. Page snapshots cached per URL. Re-observe only the failing step.Browser time, and input tokens per round.
First failure only. Send the first failing check and the last 20 or so lines of the error, not the full test output.Input per round.
Cheap checks first. Lint and the interface check run in under a second. The slow browser fill runs only if they pass.Wall-clock time.
Short, stable prompt prefix. System prompt, interface and worked example stay identical every round, so the local server's prefix cache (vLLM / llama.cpp) reuses them.Prompt processing time on every round after the first.
Fresh context per step. Don't carry the whole history. Each try gets the current step, its error, and the last 3 notes.Context stays small, and the model stays focused.
Short notes, no long reasoning. Ask for one line of "why" and then the edit. Use structured output (JSON tool calls).Output.
Low temperature. Fewer random retries.Rounds.

The log records tokens in and out for every round, so it's easy to see which step is expensive and trim it.

"Sahi" ka matlab (checks)

  1. Har step live page par chalta hai aur uska apna check pass hota hai (value wapas padhi gayi, ya agla page khula).
  2. File valid Python hai aur lint pass karti hai.
  3. Sandbox rules: sirf helpers aur allowed imports, koi submit call nahi, credentials padhna nahi, target site ke bahar koi network call nahi.
  4. Job link se shuru hone wala full test har sample job par final review page tak pahunchta hai, har required field bhara hai aur resume attached hai.
  5. Wahi steps.py us company ki har sample job par pass hota hai. Yahi "same company ke liye same code" ka proof hai.

Baad mein improve karna (kaam karne ke baad)

  • Har real run bhi ek fill report likhta hai. Agar site badalne ki wajah se run fail ho, to loop repair mode mein chalta hai: saved steps failing step tak chalte hain, aur sirf wahi step fix hota hai.
  • Failing job link tests.yaml mein add ho jata hai, to fix ko purane samples aur naye wale, dono par pass karna padta hai.
  • Fixes chhote edits hote hain, isliye jo diff main review karta hoon woh chhota rehta hai.

5. Action log: agent jo bhi kare uska note

Har tool call aur har decision usi waqt likha jata hai, taaki main baad mein build follow kar sakoon aur dekh sakoon ki kyun fail ya pass hua.

  • actions.jsonl: har action ki ek line, machine-readable.
  • actions.md: wahi steps simple sentences mein, ek nazar mein padhne layak.
  • Fields: time, round, actor (qwen / harness / human), tool, chhota input, result (pass/fail plus ek line ki wajah), tokens in/out, kitne seconds lage.
  • Log mein kabhi passwords, cookies ya asli personal data nahi hota. Profile ki values masked hoti hain (first_name=***).

6. Kam tokens, taaki code jaldi bane

Local 30B model par kam tokens ka matlab hai fast rounds. Neeche ka har tareeka model mein jaane ya bahar aane wala text kam karta hai.

TareekaKya bachta hai
Edits, rewrites nahi. Qwen poori file kabhi dobara nahi bhejta. Fix ek step ke andar ek edit_file call hai (purana text → naya text).Output: ek fix lagbhag 100 tokens ka, 1,500-token ki poori file ke bajaye.
Ek baar mein ek step. Har prompt ek page par ek action ke baare mein hai: us page ka trimmed view, ab tak ke steps ke naam, aur profile keys.Input: chhote prompts, aur galti usi field par pakdi jati hai jahan hoti hai.
Helpers, raw browser code nahi. Qwen click / fill / pick / upload / check call karta hai, aksar har field ke liye ek line.Output, aur browser timing ke bugs kam.
Trimmed page view. Accessibility tree plus network calls, raw HTML kabhi nahi. Hidden, decorative aur duplicate nodes hata do.Input: aksar HTML se 50–100× chhota.
Ek baar probe, phir reuse. Har URL ka page snapshot cache. Sirf failing step dobara observe karo.Browser time, aur har round ke input tokens.
Sirf pehla failure. Pehla failing check aur error ki aakhri 20 ke aas-paas lines bhejo, poora test output nahi.Har round ka input.
Saste checks pehle. Lint aur interface check ek second se kam mein chalte hain. Slow browser fill tabhi jab yeh pass hon.Wall-clock time.
Chhota, stable prompt prefix. System prompt, interface aur worked example har round mein same rehte hain, to local server ka prefix cache (vLLM / llama.cpp) unhe reuse karta hai.Pehle round ke baad har round mein prompt processing time.
Har step ke liye fresh context. Poori history saath mat le jao. Har try ko current step, uska error, aur aakhri 3 notes milte hain.Context chhota rehta hai, aur model focused rehta hai.
Chhote notes, lambi reasoning nahi. Ek line ka "kyun" maango aur phir edit. Structured output (JSON tool calls) use karo.Output.
Low temperature. Random retries kam.Rounds.

Log har round ke tokens in aur out record karta hai, to aasani se dikh jata hai kaunsa step mehenga hai aur use trim kiya ja sakta hai.

8. Abhi decide karna hai

  • Kya test fills test candidate account par chal sakte hain, ya har site ek insaan ko ek hi real account deti hai?
  • Kya limits theek hain (har step 8 tries, har company 60, 3 same failures)?
  • Kya kisi chalti company ka scratch se dobara build ek regular benchmark hona chahiye, jo prompts badalne par har baar chale?
  • tests.yaml ke liye 1–2 aur HCLTech sample postings dhoondhni hain.
  • Form ke beech mein koi step fail ho, to agli try job link se dobara shuru ho, ya page jaisa hai waisa rakha jaye?
  • Intent doc abhi bhi resolver + shared driver files describe karta hai. Use step-by-step steps.py format ke saath match karna hai.

Baad mein: reuse check

  • Build se pehle chalne wala ek step: link ko fillers/ ke saved fillers se match karo. Agar is company ka filler hai, to build skip karo aur seedha form bharo.
  • Tab tak har link par naya build hoga, chahe company pehle ban chuki ho. Files phir bhi reusable format mein save hoti hain, to baad mein check bina unhe badle add ho sakta hai.
